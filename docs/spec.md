## 1. Vision and overview

**Gritos** is a decentralized chat application that runs entirely in the browser, **with no backend of its own and no user accounts**. WebRTC signaling is resolved through public BitTorrent trackers (via **Trystero**, _torrent_ strategy); once the data channel is established, messages travel directly between browsers (a _full mesh_ topology) encrypted by DTLS, with additional E2EE layers for direct (1:1) messages and for rooms protected by a password.

Guiding principles:

1. **No server**: all code is client-side; the deployment is a static bundle.
2. **No accounts or sign-up**: identity is a nickname + a locally generated key pair.
3. **Ephemeral by default**: messages exist only in memory; on reload, they disappear.
4. **Minimal persisted-data surface**: only settings and the cryptographic identity remain in `localStorage`.
5. **Minimalist, fast, clean UI**: a single conversation column, collapsible sidebar, zero ornament.

## 2. Closed product decisions

| #   | Decision                                          | Choice                                        | Main consequence                                                                                              |
| --- | ------------------------------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| D1  | Room topology                                     | **Multiple simultaneous rooms from v1**       | Each active room keeps its own WebRTC mesh; a configurable active-room limit applies (default 4, max 6).      |
| D2  | Message history                                   | **Memory only**                               | No message is persisted; no IndexedDB; no _gossip_ sync between peers. Late joiners see no previous messages. |
| D3  | v1 content                                        | **Text / Markdown only**                      | No file or image transfer (phase 2).                                                                          |
| D4  | Additional encryption                             | **1:1 DMs with E2EE + shared-password rooms** | ECDH P-256 + AES-GCM for DMs; PBKDF2 + AES-GCM for password rooms.                                            |
| D5  | Per-room capacity (derived from the architecture) | Small groups                                  | Full mesh: optimal 6–15 peers per room; acceptable degradation up to ~20.                                     |

> **Note on D2**: the "memory only" decision applies to **content** (messages, typing, presence). **Settings** and the **cryptographic identity** do persist in `localStorage` (section 8.2) because the experience needs them (theme, trackers, stable nickname) and they are part of wishlist section 5. The _panic button_ (RF-08) wipes absolutely everything.

## 3. Scope

### 3.1 In scope (v1)

- Onboarding with a nickname (manual or autogenerated) and auto-join to `#lobby`.
- Rooms: suggested (`#lobby`, `#general`, `#dev`, `#random`), join by free name, multiple simultaneous rooms, leave room.
- Rooms with a shared password (roomId derived from the password → hidden existence at the tracker).
- Real-time text messaging with a safe basic Markdown subset, typing indicators, delivery receipts and mentions.
- 1:1 E2EE-encrypted direct messages between peers sharing at least one room.
- Presence with connection state and a per-peer latency indicator.
- Settings: custom trackers, custom STUN/TURN, auto-join, theme, desktop notifications, active-room limit.
- Privacy: local muting of peers by fingerprint (issue #95), identity regeneration and the _panic button_.
- Light / dark / system theme.
- Deployment as a static site.

### 3.2 Out of scope (v1)

- P2P file and image transfer.
- History synchronization between peers (_gossip / state sync_) and local message persistence.
- Massive rooms (>20 peers) or relay topologies (SFU).
- Editable or deletable messages, nested replies (_threads_), reactions.
- A project-run TURN of its own (only user-configured external TURN).
- PWA / offline operation, i18n (the UI is hardcoded English, issue #112), native applications.

## 4. Functional requirements

Each requirement includes verifiable acceptance criteria. The `RF-xx` prefixes are used as references throughout the development plan.

### RF-01 · Onboarding

The user opens the URL and, if there is no local identity, is presented with a centered screen showing the app name, a nickname field and a "surprise me" button that autogenerates a friendly English nickname (format `noun-adjective`, e.g. `fox-bold`, `moon-wary`).

**Acceptance**

- The nickname allows 2–24 characters (`letters, numbers, space, hyphens, underscores`); excess whitespace is trimmed and normalized.
- With an empty field, "Enter" generates a valid random nickname.
- After entering, if `autoJoinLobby` is on (default yes), the app automatically joins `#lobby`.
- The identity (nickname + keys) is stored in `localStorage`; on later visits it is not asked again.
- The nickname can be changed at any time from settings; the change is announced to connected peers.

### RF-02 · Rooms

The user can be connected to **several rooms at once**. Joining a room does not exist as a server action: it is subscribing to a common identifier at the tracker.

**Acceptance**

- Suggested rooms visible: `#lobby`, `#general`, `#dev`, `#random`; a click joins (if there is room).
- Join by free name: normalization `trim + lowercase + whitespace→'-'`, only `[a-z0-9_-]`, length 1–32. Invalid name → inline error message, no error modal.
- Simultaneous active-room limit: configurable (1–6, default 4). An attempt above the limit → the "Active room limit reached (N)" notice.
- At the limit, the UI offers to leave an active room to join the new one.
- Each active room shows its own connection state (section 10.3) and peer count.
- "Leave room" closes its connection (frees the mesh) and removes it from the list; optionally it is recorded under Recents.
- Recent-rooms list (names only, never content) when `rememberRooms` is on; a click rejoins the room. Password-room names are never recorded and an earlier entry is purged when joining with a password (issue #31).
- Switching the active room does not interrupt the other connections; messages arriving in non-active rooms raise their unread badge.

### RF-03 · Room messaging

Sending and receiving text in real time in the active room.

**Acceptance**

- Multiline input: `Enter` sends, `Shift+Enter` inserts a line break; the field grows up to 6 lines.
- Maximum message length: 4000 characters; the UI indicates it and blocks sending above it.
- **Limited and safe** Markdown rendering: `**bold**`, `*italic*`, `` `code` ``, ``` blocks, `[text](https://…)` with `http`/`https` schemes only, line breaks. **No raw HTML** (everything is escaped) and no images/video (D3).
- Mentions: the text `@nickname` highlighted when it matches (case-insensitively, word-bounded) your own nickname or that of present peers.
- Typing indicators: while typing, `typing` is emitted with a 1 s throttle; the state expires after 4 s. "N people are typing…" is shown under the feed.
- Delivery receipts: each own message shows `✓` (sent) and `✓✓` when **at least one peer** confirms receipt. In a single-occupant room only `✓` is seen.
- Smart scroll: auto-scroll only if the user is ≤150 px from the bottom; otherwise a floating "↓ N new messages" button jumps to the end and clears the counter.
- Memory cap: at most the last **500 messages per room** are retained (FIFO discard, announced in the feed with a "— earlier messages discarded —" separator).
- Clock: each message shows the local `HH:MM` time from the author's `ts`.

### RF-04 · Direct messages (DM) with E2EE

Private 1:1 conversation with any peer sharing at least one active room.

**Acceptance**

- From a room's peer list, clicking a peer → "Direct message". The DM conversation opens (a room-like view, header with the other's nickname and their _fingerprint_).
- All DM messages travel E2EE-encrypted (section 9.2); nobody else —not even other peers of the shared room— can decrypt them.
- The DM header shows the peer's fingerprint (section 9.1 format) with the notice "Compare it with your contact to verify their identity".
- DMs inherit Markdown, typing, receipts, smart scroll and the 500-message cap.
- Per-DM unread badge; unread DMs are notified (RF-09) when the tab is hidden.
- A DM stops being able to send when the peer leaves all shared rooms: the "The peer has disconnected" state, and the DM history remains visible in memory until reload.
- Documented limitation, visible in the UI: there is no DM with peers who share no room (no global channel exists; see 11).

### RF-05 · Shared-password rooms

A room whose content is encrypted with a key derived from a password and whose **very existence is hidden** at the tracker.

**Acceptance**

- When joining/creating a room, an optional "Password (encrypted room)" field. If set, the room is marked with 🔒 in sidebar and header.
- The `roomId` announced to the tracker is derived from `hash(appId + name + password)` (section 9.4): whoever lacks the password **cannot discover or enter** the room — it is not that they cannot read, it is that they cannot find it.
- All room messages travel encrypted with AES-GCM-256 derived from the password (PBKDF2). The password lives only in session memory; **it is never persisted**.
- If a peer managed to enter without the key (theoretical colliding-derivation scenario), they would see only the "🔒 encrypted message" placeholder — never plaintext.
- A wrong password = a nonexistent-room error: the same "Room #name not found with that password" message (it does not disclose which of the two failed).
- On page reload, password rooms must be rejoined by re-entering the password.

### RF-06 · Presence and latency

**Acceptance**

- Per room, a list of connected peers with nickname and colored latency dot: 🟢 <150 ms, 🟡 150–400 ms, 🔴 >400 ms, ⚪ no data (no answer yet, or degraded).
- Measurement: `ping`/`pong` every 5 s per peer and room; 3 consecutive failures → degraded ⚪ state until an answer returns.
- When a peer connects: nickname, fingerprint and public key are announced (`presence` + `keys` actions).
- Duplicate nicknames in the same room are shown with a short peerId suffix (`fox-bold·a3f1`) to disambiguate.
- Peer joins/leaves are reflected in the feed with discreet system lines ("— moon-wary joined —").

### RF-07 · Settings

A modal with three tabs. Every change is saved to `localStorage` instantly.

**Network**

- Auto-join `#lobby` on start (on/off, default on).
- Custom trackers (editable list of `wss://` URLs). If the list is empty, Trystero's defaults are used; if the user defines a list, it **replaces** the defaults.
- Custom ICE (STUN/TURN) servers (an editable `stun:host:port` / `turn:host:port` list with user and password for TURN). Empty list = Trystero's default configuration.
- Active-room limit (1–6, default 4).
- Note in the tab: "Network changes are applied when the rooms reconnect", with a "Reconnect all" button.

**Privacy**

- Desktop notifications (on/off + an "Allow notifications" button that requests the permission).
- Remember recent rooms (on/off, default on).
- Regenerate the cryptographic identity (with confirmation and a warning that the fingerprint changes and the DM keys stop matching).
- Muted peers (issue #95): a local list of peers muted by fingerprint, with a button to unmute; the nickname is shown only if the mute dates from the current session.
- _Panic button_: "Wipe everything and leave" (see RF-08).

**Appearance**

- Theme: Light / Dark / System (default System).
- Initial sidebar collapsed state (remembered).

### RF-08 · Panic button

**Acceptance**

- Button in Settings → Privacy with explicit confirmation ("Nickname, keys, settings and every local trace will be wiped. Continue?").
- On confirm: clears **all** `gritos:*` keys from `localStorage`, aborts every WebRTC connection, empties the in-memory state and reloads the application.
- After the reload, the app appears as a first visit (clean onboarding).

### RF-09 · Desktop notifications

**Acceptance**

- Via the Web Notifications API, only if the permission was granted and the setting is on.
- Only these are notified: (a) an `@mynick` mention in any room, (b) an incoming DM message — as long as `document.hidden === true`.
- The notification shows author and room/DM; the body text is shown in the clear (UX decision: the notification is local to the receiver's device).
- Clicking the notification focuses the tab and opens the corresponding room or DM.
- Without the permission granted, the setting stays disabled with an explanation of how to enable it.

### RF-10 · Themes

**Acceptance**

- Light, Dark and System (live sync with `prefers-color-scheme`).
- Switching without reloading the page or losing state; respects a minimum AA contrast.

## 5. Non-functional requirements

| ID     | Category               | Requirement                                                                                                                                                                                                                  |
| ------ | ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RNF-01 | Data privacy           | No message content, room password, peer private key or conversation metadata ever leaves the device toward `localStorage` or external parties. The only persistent writes are those of section 8.2.                          |
| RNF-02 | Cryptographic security | Everything encrypted uses Web Crypto (subtle) exclusively. AES-GCM-256 with a random 96-bit IV per message; ECDH P-256 + HKDF-SHA256 for DMs; PBKDF2-SHA256 ≥600,000 iterations for rooms. No hand-implemented cryptography. |
| RNF-03 | Performance            | Perceived interaction <100 ms when sending a message; the mesh supports 15 peers per room with 4 KB messages without perceptible loss; memory bounded by the message caps (500/room) and rooms (≤6).                         |
| RNF-04 | Compatibility          | Latest stable versions of Chrome, Edge, Firefox and Safari (mobile included). Requires a secure context (`https://` or `localhost`) for Web Crypto, WebRTC and notifications.                                                |
| RNF-05 | Accessibility          | Full keyboard navigation; feed with `aria-live="polite"`; modals with trapped focus and `Esc` close; AA contrast; sidebar usable as a _drawer_ on mobile.                                                                    |
| RNF-06 | Deployability          | The production build is 100 % static (`dist/`); it works on any file host (GitHub Pages, Netlify, local nginx). No mandatory environment variables or external services.                                                     |
| RNF-07 | Network traceability   | Every connection state is visible to the user (never an indistinguishable "silence" that could hide a failure).                                                                                                              |

## 6. Architecture

### 6.1 Overall diagram

```
┌───────────────────────────── Browser A ──────────────────────────────┐
│                                                                      │
│  UI (React + Tailwind)                                               │
│    │ useAppStore / useSettingsStore (Zustand)                        │
│    ▼                                                                 │
│  RoomManager (lib/p2p)  ── one Trystero instance per active room     │
│    │ joinRoom / makeAction / onPeerJoin / onPeerLeave / leave        │
│    ▼                                                                 │
│  CryptoLayer (lib/crypto)  ── identity, DM keys, room key            │
│    ▼                                                                 │
│  WebRTC DataChannels (DTLS) ════════════════════════╗                │
└─────────────────────────────────────────────────────╫────────────────┘
                                                      ║ (direct P2P,
┌───────────────────── BitTorrent trackers (wss://) ──╫── signaling
│  initial SDP handshake (offers/answers)             ║   only)
└─────────────────────────────────────────────────────╫────────────────┘
                                                      ║
┌───────────────────────────── Browser B ─────────────╫────────────────┐
│  same architecture  ════════════════════════════════╝                │
└──────────────────────────────────────────────────────────────────────┘

The trackers only take part in the initial _discovery_ and SDP exchange. Application traffic never passes through them.

### 6.3 Room connection flow

1. The user picks a room (and an optional password). `roomId = hash(appId + name [+ password])` is computed (9.4).
2. `joinRoom(config, roomId)` with `config = {appId, trackers?, rtcConfig?}`.
3. Trystero opens WebSockets to the trackers and announces its peerId under the roomId hash.
4. Another client with the same roomId receives the peer list; they exchange SDP offers/answers **through the tracker**.
5. A direct DataChannel is established (DTLS). `onPeerJoin(peerId)` fires on both sides.
6. When a peer joins: immediate send of `presence` (nickname, fingerprint) and `keys` (the ECDH public key). The `ping/pong` loop starts.
7. The trackers stop being necessary while the tab lives; if they fall, the already-connected peers keep communicating (only the ability to discover new peers is lost).

### 6.4 Room message flow (no password)

1. The author writes → `Envelope{kind:'chat'}` → `sendChat(envelope)` broadcast to the room's peers.
2. Each receiver: validates `v`, dedups by `id`, decrypts if `enc`, adds to the store, smart-scrolls if appropriate, emits a `receipt` directed at the author.
3. The author marks `✓✓` with the first `receipt` received.
4. With a password: `body` = base64(IV ‖ AES-GCM ciphertext) and `enc: true`; otherwise identical.

### 6.5 Multi-room management

- `RoomManager` keeps a `Map<roomId, RoomConnection>`; each `RoomConnection` encapsulates its Trystero instance, its registered actions and its ping loop.
- Joining/leaving is independent per room; the active-room cap is validated in the manager before calling `joinRoom`.
- Peers are identified by a global peerId (Trystero); the same peerId in two rooms is the same peer — the UI's "peers" list aggregates per room and the DM uses the first available shared channel.

### 7.2 Message envelope (`Envelope`)

```jsonc
{
  "v": 1, // per-kind version: chat and the control plane require v=1, dm requires v=2 (issue #93); any other value → ignore silently (7.3)
  "id": "uuid-v4", // crypto.randomUUID() — deduplication
  "ts": 1760000000000, // the author's Date.now()
  "from": "peerId-trystero",
  "nick": "fox-bold", // the author's nickname at send time
  "kind": "chat", // "chat" | "dm"
  "to": "peerId", // only in kind:"dm"
  "enc": false, // true if body is base64(IV ‖ ct)
  "iv": null, // base64 of 12 B when enc
  "body": "hello world", // plaintext | base64(ciphertext) | max 4000 chars in the clear
  "ttl": 300, // optional (issue #96): expiry in whole seconds, 30–3600 inclusive; absent = the message lives for the whole session (7.3)
}
```

**The `ttl` field (issue #96)** is additive and **introduces no new version**: `v` remains per `kind` — `chat` v:1, `dm` v:2 (issue #93) — and an envelope with `ttl` travels with exactly the version its `kind` calls for. The mixed-build degradation is the one already documented in 7.3 for unknown fields: an old build ignores the field silently and **keeps the message for the whole session** (it never fails to parse it). A present but invalid `ttl` (0, negative, out of range, non-integer, non-numeric) invalidates the **whole envelope**, which is discarded like any other field violation — never just the field, so a message cannot silently degrade to a different lifetime than the one its author asked for.

### 7.3 Protocol rules

- **Deduplication**: any message whose `id` was already seen is discarded (batched receipts and the full mesh can duplicate).
- **Ordering**: messages are shown in arrival order; within a 2 s window they are ordered by `ts`. There is no consensual global order (no server) — documented as an acceptable limitation for informal chat.
- **Size**: body ≤4000 characters in the clear; binary payloads >64 KB are discarded for safety.
- **Disconnection**: `onPeerLeave` clears the peer's presence and typing in that room; their DMs go into "peer disconnected" mode.
- **Compatibility and versioning**: unknown Envelope fields are ignored; `v` is discriminating per `kind` — `chat` requires `v: 1` and `dm` requires `v: 2` (issue #93) — and any other value is silently discarded. In rooms with mixed builds, a v1 peer silently drops v2 `dm`s and a new peer drops v1 `dm`s, in both directions, until the builds converge (12.1). The `ttl` (issue #96, 7.2) is the canonical example of an additive field: an old build ignores it and keeps the message for the whole session — expiry is each receiver's courtesy, never a sender's guarantee.
- **Per-message expiry (issue #96)**: an envelope with `ttl` (7.2) expires **on the receiver's clock**: when adding it to the feed, each peer computes `expiresAt = receivedAt + ttl·1000`, where `receivedAt` is the local `Date.now()` of that instant — the author's `ts` is only tolerated with a ±90 s skew and **is never used to expire**. A 1 s sweep (a single timer per session, across all rooms and DMs; the scan is bounded by the 500-per-feed FIFO cap) removes the expired message — inclusively: `expiresAt ≤ now` — and without `ttl` the message lives for the whole session (the FIFO cap remains the only eviction; an expired message **frees its slot** before the cap can matter). The removal leaves a local "— N expired messages —" separator (the mirror of the FIFO one), memory-only and cumulative per feed while it lives. Two guarantees of the sweep: **no resurrection** — the removed ids enter a bounded set of expired ones, so a repeat of an envelope whose dedup entry was already evicted is discarded before any effect (no feed row, no receipt, no mention) — and **no retro-touch** — receipts already delivered are not revoked, and the unread counts and notifications (mentions and DMs, RF-09) raised at reception are not undone: expiry only mutates the feed.
- **Opt-in history gossip (issue #102)**: a peer who joins late may ask for the recent history (7.1, `hist-req` — one explicit tap, never automatic, budgeted at 1 request/minute per room) and only the peers who consented (`shareHistory`, 8.1, **false** by default) answer by replaying at most the last 50 chat messages of their in-memory feed as `hist` (7.1) — never system lines, encrypted placeholders or already-expired rows, and **never DMs** (room scope). The replay rules at the receiver: the shape validation is complete (`parseEnvelope`: the `chat` v:1 gate, shapes, body caps, `ttl` validity) and the ONLY freshness rule relaxed is the 5-minute age window (issue #19) — a deliberate bypass, which is the point of gossip: what is recovered is older than 5 minutes by definition —; the ±90 s future skew is kept per envelope (`isWithinFutureSkew`), because a far-future timestamp would stay "fresh" —and above the recovered block— for hours. Deduplication holds in both directions: the ids of a batch are marked seen on arrival, so a later LIVE resend of the same id falls (and an id received live earlier makes its replayed copy fall). Zero arrival effects: no unread, no mention notification, no receipt (✓✓ means live delivery), no typing. Reception cap: at most 50 recovered per join session and room (`MAX_RECOVERED_PER_JOIN`); the excess of later batches is silently dropped. Ordering: the 2 s window (the Ordering rule, above) does NOT apply to replayed rows — a batch replays history whose author `ts` is far from any arrival window, and re-ordering by `ts` would shuffle the block —: rows are appended in batch order (the wire's), the same old→new order in which the sharer cut their slice. Muted-author gate (issue #95, parity at append time): the fingerprint of the replayed envelope's AUTHOR —its `from`, not the sharer's— is resolved against the keys announced to THIS connection, and a muted author is dropped; if their keys never landed here, it fails open like the live path (above). `ttl` in recovery: `expiresAt = Date.now() + ttl·1000` on the RECEIVER's clock at append time — never derived from the author's `ts`, so a zombie is not resurrected — and an id already swept by expiry (issue #96) never resurrects through gossip. Password rooms: `enc` envelopes are opened with the room key (a plaintext row) or remain the "🔒 encrypted message" placeholder if they fail to open — the raw ciphertext never lands as text, and an `enc` envelope reaching a keyless room is discarded. Provenance and trust: recovered rows render slightly dimmed under the "— messages recovered from peers —" separator, which labels the provenance honestly — a gossiping peer can FORGE history (fake old messages) at the same level of trust as live chat (9.5, unauthenticated control plane). Nothing is persisted: the shared set dies with the tabs holding it, just like the messages — the panic button (RF-08) needs nothing special.
- **Silence**: a received message is never relayed to third parties (no relay in v1; the `to` of someone else's `dm` is ignored and dropped).
- **Local mute (issue #95)**: the `mutedFingerprints` list (8.1) filters the receive paths by the peer's identity fingerprint — the one derived from their announced keys (9.1), not the self-declared `fp` of the `presence` announce. From a muted peer, the following are discarded: the room `chat`, before parsing, deduplicating, adding to the feed, evaluating mentions (and their notification, RF-09) or queueing the receipt; the directed `dm`, before any work (no new channel, no dedup slot, no decryption); the `typing` indicators (room and DM); and the join/leave system lines — the peer stays "unannounced": with the mute lifted, their next `presence` reveals the deferred line. From that same peer, `receipt` and `ping/pong` keep being processed (the ✓✓ and the latency dots stay honest) and the `keys`/`ephkeys` announces with their TOFU pin (8.2). Race: an envelope arriving before the author's key announce is processed (_fail-open_; the announce lands in the same join burst, 6.3).

A reload loses everything but those pins: global channels are per session, like the room and manual ones.

## 9. Cryptographic design

Everything with Web Crypto (`crypto.subtle`). No hand-implemented primitives.

### 9.1 Identity

- An **ECDH P-256** key pair generated locally on first boot (or when regenerating the identity).
- The public key exported raw (65 B) for the exchange; the public JWK persisted in the clear and the **private JWK encrypted at rest** (issue #24): wrapped with AES-GCM under a non-extractable key kept in IndexedDB — a different store from `localStorage`, so a dump of the latter no longer suffices to steal the identity. Without IndexedDB the envelope degrades to plaintext (an accepted trade-off: same origin, no server; see the threat model).
- **Fingerprint** = SHA-256(raw public key) → hex, the first 16 bytes (128 bits) in 8 groups: `A31F 09BC 77D2 4E5A 51C0 FFEE 1234 5678`. It serves for manual identity verification in DMs (TOFU). Issue #23: 128 bits raise the cost of a birthday collision from ~2³² to ~2⁶⁴ tries. The widening is presentational only: the ECDH key and the persisted identities do not change (the fingerprint is recomputed from the key on restore).

### 9.2 DM key (1:1)

The derivation in force is the **v2** one (issue #93; design note in 12.1): the DM secret comes from a **session-ephemeral** ECDH, not from the long-lived identity keys.

1. Each peer generates an ECDH P-256 pair **ephemeral per app session** at boot (and regenerates it with the identity): it lives only in memory, is never persisted —neither `localStorage` nor the IndexedDB store— and the panic button wipes it (RF-08). Its raw public key (65 B) is announced with the directed `ephkeys` action on connect and after regenerating the identity (7.1). #97's manual DM channels (12.2) have no `ephkeys` announce —there is no swarm to hang it on—: their ephemeral key travels inside the invite blob and the derivation is exactly this section's.
2. The announce is stored next to its fingerprint **without a TOFU pin**: only the identity fingerprint is anchored in `gritos:tofu` (8.2) and only the identity is displayed for manual verification (9.1, RF-04). A substituted ephemeral key does not derive the same DM key: the dual salt of point 4 makes the GCM fail visibly.
3. To send or receive, each end computes `secret = ECDH(myEphemeralPriv, theirEphemeralPub)` → 256 bits.
4. `dmKey = HKDF-SHA256(secret, salt = SHA-256(the four canonical fingerprints sorted ascending: identity and ephemeral of both ends), info = "gritos/dm/v2", 32 B)` → a **non-extractable** AES-GCM-256 key (_dual salt_: with both fingerprint pairs in the salt, the identity→ephemeral binding is tied without signatures; see 12.1). The `fp`s are 9.1's in canonical form (no spaces, uppercase); each end computes its own from the announced raw keys.
5. Each DM message: a random 12 B IV; `base64(IV ‖ AES-GCM(text))` is transmitted in a `dm` envelope with `v: 2` (7.2).
6. The key lives only in memory, in a per-session per-peer cache (keyed by the sorted fingerprints); it is not persisted. When the session closes, the ephemeral private key disappears and what was recorded stops being decryptable (12.1).

**Legacy v1 format (no longer sent nor accepted).** The original static-static derivation —ECDH between identity keys, salt = SHA-256(fpA ‖ fpB sorted), `info = "gritos/dm/v1"`, a `dm` envelope with `v: 1`— remains in the code only as a reference to the old format. The parser rule is final: `chat` requires `v: 1` and `dm` requires `v: 2` (7.3). In rooms with mixed builds, the envelopes that fail to open are silently discarded in both directions; the new peer additionally sees an explicit legacy-peer state —composer disabled: "This peer runs an older version without per-session encrypted DMs"— instead of a silent loss of messages. There is no key migration: channels and DM keys live only in memory (the 128-bit fingerprint widening, issue #23, already changed the salt deliberately and uniformly in v1).

### 9.3 Password room key

1. `salt = SHA-256("gritos/room-salt/v1/" + normalizedName)` — deterministic and public (not a secret; it avoids per-room rainbow tables).
2. `roomKey = PBKDF2-SHA256(password, salt, 600,000 iterations, 32 B)` → AES-GCM-256.
3. Encryption identical to the DM's: a 12 B IV per message, `base64(IV ‖ ct)`.
4. The password exists only in session memory; on reload it must be re-entered.

### 9.4 `roomId` derivation

- Public room: `roomId = hex(SHA-256("gritos/room/v1/" + name))[0..31]`
- Password room: `roomId = hex(SHA-256("gritos/room/v1/" + name + "\u0000" + password))[0..31]`

The password derivation makes the room **undiscoverable** at the tracker without the password (decision D4). Trystero's `appId` is no longer a code constant: it is taken from the `VITE_TRYSTERO_APP_ID` build environment (issue #90, template in `.env.example`, resolution in `lib/p2p/appId.ts`). The value is baked in at build time and, when missing, joining rooms fails immediately instead of falling back to a silent default (a shared fallback would fork the swarm without warning).

### 9.5 Threat model

**Covered**

- Passive network observers (ISPs, trackers): they see DTLS and, in encrypted rooms and DMs, only ciphertext.
- Public tracker operators: they see only roomId hashes, peerIds and SDP; in password rooms, not even the hash exists for whoever lacks the password.
- Malicious peers inside a password room: they cannot decrypt the room or other people's DMs.

**Not covered (documented, accepted)**

- Nickname impersonation: any peer can use another's nickname; the defense is comparing fingerprints in DMs (TOFU — _trust on first use_), with no global persistent identity base.
- Unauthenticated control plane (issue #36): the signals outside chat content —`receipt` confirmations (the ✓✓), "typing…" (`typing`), "joined / left" system lines, latency `pong` echoes and emoji reactions (`react`, issue #98)— travel without message authentication, so any peer can forge them (mark other people's messages delivered, fake typing, emit system lines with arbitrary nicknames —which also displace real history through the 500-message FIFO—, inflate the latency dots or inflate the reaction counts of other people's messages —issue #98: the displayed count is the local sum of unauthenticated payloads— or forge (or bias) the history the opt-in history gossip relays —issue #102: the same level of trust as live chat; the "— messages recovered from peers —" separator labels provenance, not veracity (7.3)—) or flood chat to saturate unread badges and mention notifications. It is inherent to v1's trustless mesh —the same root as nickname impersonation, above—; v1's mitigation is cosmetic: a per-peer per-minute system-line cap, negative-RTT discard and clamping of absurd RTTs in the `pong` echo — and for the reactions (issue #98) a 7-emoji whitelist, batches ≤50 ids, a cap of 30 payloads per peer per minute and state caps of 50 reactions per emoji (the 51st peer is rejected, never evicted). Issue #95 adds the first on-request mitigation —muting peers by fingerprint: the local list of 8.1/8.2 (exact semantics in 7.3) hides the room chat, DMs, typing, the system lines and reactions (issue #98) of the muted peer—. Accepted limits, consistent with the trustless mesh: rotating the identity key evades the list (the TOFU pin, 8.2, makes the rotation visible with its changed-key warning) and the race window until the peer's announced keys land fails open (7.3).
- Device or origin compromise (XSS): the private key is stored encrypted at rest (issue #24), but a script of the origin itself has access to `localStorage` **and** IndexedDB, so a fully compromised context can still use the key (impersonate the user). Mitigation: the wrapping raises the bar against naive `localStorage` dumps (extensions with read permissions, physical disk access); against the origin's own compromise there is no local defense. The home-grown Markdown renderer with its XSS tests and the minimal dependency surface remain the first barrier.
- Metadata: connected peers see your IP (the nature of WebRTC); using TURN partially mitigates it.
- Global signaling channel exposure (issue #105, 12.5): whoever turns the global DMs on joins a public, well-known swarm —all builds with the setting active share the room—, so **every opt-in peer sees your IP** (the same WebRTC nature as the point above), **your identity fingerprint and your nickname**. The documented mitigation is the toggle itself: `Settings.globalDm` is **off by default** and joining is a visible privacy decision of the user, never a silent behavior; 12.5's caps (the LRU-100 presence, 5 knocks per peer per minute) and the mute list (issue #95) bound the abuse. A knock also reveals the knocker's interest in the knocked — inherent to the mechanism: directing a `knock` IS declaring that you seek that fingerprint; the note field is optional and ≤ 140 characters.
- Cryptanalytic advances / a weak room password: PBKDF2 raises the cost, but a trivial password remains brute-forceable offline by anyone who knows the room name. In the DMs, the _harvest now, decrypt later_ risk (issue #25) is **mitigated to session scope** with the v2 derivation (issue #93; 9.2): when the session closes, the ephemeral private key disappears and what was recorded stops being decryptable. Residual risk, plainly: capturing the traffic **during** an active session and later compromising the device exposes that session —and enables impersonation until the TOFU rotation alert (8.2)—. v1 peers, and what was recorded in v1 before the migration, remain under the original static-static exposure (12.1).

### 10.7 Slash commands (issue #99)

A 100 % client-side feature: no protocol change whatsoever (section 7 stays intact). The composer interprets input starting with `/` + verb; the verbs are English and lowercase-only (a product decision: they are documented, not localized), with strict arity — an argument to a zero-argument command is an error, never silently ignored. All feedback is local system lines (the pattern of #95's mute lines): they never travel the network.

| Command        | Semantics                                                                                                                                                                                                                                                                                                                                     |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/nick <name>` | Renames under the RF-01 rules (the same validations as onboarding) and re-announces `presence` in every active room; the author color keeps deriving from the peerId.                                                                                                                                                                         |
| `/room <name>` | A focused join through the same path as the "+ Join" popover (RF-02 normalization); the cap rejection prints the exact RF-02 notice (#87 fix). On success it **arms the password offer**: if the room ends up peerless (the `error` state), that room's prefilled popover appears — the password flow fires only when it is genuinely needed. |
| `/dm <nick>`   | Resolves among the active room's peers (case-insensitive exact match; the user themselves is never a candidate). A single match → opens the DM; ambiguity or absence → a local error line, never a guess.                                                                                                                                     |
| `/me <action>` | Sends a normal `chat` envelope (the wire does not change) with a **local render flag**: the author sees "_nickname action_" in italics; peers see plain text — the documented asymmetry of the rendering convention with no protocol change.                                                                                                  |
| `/rooms`       | A local line with the active rooms and their unread counters.                                                                                                                                                                                                                                                                                 |
| `/clear`       | Empties the active room's local feed after confirmation: memory only — the connection is not closed and peers keep their history.                                                                                                                                                                                                             |
| `/leave`       | Leaves the active room through the same path as the sidebar menu (only the focused room; the other connections continue).                                                                                                                                                                                                                     |
| `/help`        | A local overlay with this command table.                                                                                                                                                                                                                                                                                                      |

Cross-cutting guarantees:

- **An unknown verb is never sent**: `/foo …` produces only the local "Unknown command — /help" line — no literal text with `/` reaches the network by accident. To send a message that starts with `/` there is the escape documented in `/help`: `\/hello` sends "/hello" (the backslash is removed on send).
- **Keyboard autocomplete (RNF-05)**: when typing `/`, the composer opens a candidate popup with the ARIA combobox pattern — the textarea is `role="combobox"`, the list `role="listbox"` with `aria-activedescendant`, options never focusable: focus never leaves the textarea; `↑ ↓ Enter Esc` govern the list, and a verb with no candidates opens no popup.
- **Every command is operable with the keyboard alone**, from opening the popup to execution.

### 10.8 Room sharing and QR invite code (issues #41 and #100)

The header's "⤴" button shares the room's deep link — `origin + path + #sala=<name>` (built by `buildRoomLink`, consumed by the `#sala=` routing of the onboarding and of `ChatLayout`) — via `navigator.share` with a clipboard fallback ("Link copied"). The link carries **only the name, never the password** (RF-05).

The "QR" button (issue #100) opens a popover that encodes **exactly that same link** as a QR code: scanning it with another device's native camera lands on the join flow with the name prefilled. The QR **never contains the password** — in an encrypted room, the link only opens the join flow and signing in still asks for it (RF-05). The scan surface is **fixed**: near-black modules on white with their quiet zone, in light AND dark — scannability trumps the theme (the AA tokens guarantee contrast to human eyes, not to decoders). "Download PNG" exports the same symbol in high resolution (`gritos-room-<name>.png`), with the link as copyable text below as a fallback. The limit is documented in the popover itself ("The QR links to this same installation."): the link only works within this same installation — same origin and same `VITE_TRYSTERO_APP_ID` (issue #90); a QR from another installation joins nothing.

### 10.9 PWA installation and update flow (issue #104)

**Status: implemented (issue #104).** The app is installable (a `standalone` manifest with 192/512 icons and maskable variants, all in relative URLs — `start_url`/`scope: './'`, registration of `./sw.js` — so installation works the same under subpaths, including GitHub Pages project pages) and boots without network: a minimal, hand-rolled service worker (`public/sw.js`) precaches each build's exact shell — the document, the manifest, the statics and the hashed assets, with the `gritos-shell-v<digest>` list and cache name injected at build by a Vite plugin — and serves it cache-first. The worker's scope is the shell only and same-origin only: cross-origin traffic (the trackers' `wss:` sockets first of all) passes through and is never cached; no push, no background sync, no new channel of any kind. The offline shell is **honest** (10.3): without network the app boots and shows its real connection state — P2P still needs connectivity.

**The update flow.** The worker never calls `skipWaiting()`: a new version installs and **waits** while this page still runs the old one. The registration (`lib/pwa/registerSw.ts`) detects the waiting worker — already waiting when the registration resolves, or an `updatefound` whose install reaches `installed` while the page is still controlled by a previous worker (`controller != null`; on a first install there is nothing to update) — and the corner toast, "New version available — [Reload]" (`role="status"`, component-local state, no persistence), offers the swap. "Reload" runs `location.reload()`: the old client bows out, the waiting worker activates and the activation cleanup deletes the previous `gritos-shell-v*` caches. Dismissing the toast lasts only for the session (a NEW waiting worker notifies afresh — the per-occurrence rule of the network banner); there is deliberately no `controllerchange` listener: the swap is the user's explicit reload, never automatic — a live conversation does not lose its connections to a deploy. iOS remains documented partial support (11.10): no install prompt, occasional SW quirks. `vite dev` stays worker-free (the same philosophy as `stripCspMetaInDev`): only production builds register, only in a secure context, and a registration failure is never fatal.

## 11. Known limitations (visible or documented in the UI)

1. **Full mesh**: optimal 6–15 peers per room; from ~20 on, the mesh degrades (more active rooms multiply the effect). The room cap (≤6) and the message cap (500) mitigate memory/CPU.
2. **Public-tracker dependency**: if they all fall, no new peers are discovered (the already-connected peers continue). An alternative-trackers setting is available (RF-07).
3. **Symmetric NAT / corporate firewalls**: without TURN, direct P2P can fail. Configuring your own STUN/TURN is offered; with no guaranteed TURN, the connection is not promised.
4. **Active tab**: deeply backgrounded, the browser slows timers (degraded pings); returning to the front recovers them.
5. **No server**: no history for late joiners (D2), no delivery to disconnected peers, no real push (notifications only happen with the tab open, even hidden).
6. **Multiple tabs of the same browser**: each tab is a distinct peer; it works, but you will see your own nickname duplicated with a suffix.
7. **DMs only between peers sharing a room, except for two deliberate paths**: discovery is tracker-based, so an arbitrary DM requires a shared room — softened by the manual peer connection (issue #97; 12.2, zero infrastructure) and the opt-in global signaling channel (issue #105; 12.5, requires BOTH sides to enable `Settings.globalDm`); neither is an automatic or silent path.
8. **No global message ordering** (7.3) and **nicknames not unique** (RF-06): accepted for v1.
9. **File transfers live in RAM (issue #103, 12.4)**: received files live as in-memory blobs (up to 20 MB per file; with `MAX_TRANSFERS_PER_PEER = 3` concurrent transfers per peer on both sides, the worst case is around 60 MB per peer and direction) — several at once can strain modest devices, and the 20 MB cap plus the 3-per-peer cap are the mitigation. Nothing is ever persisted: a reload loses it all, and object URLs are revoked on dismissing the card, on aborting or failing, with panic (RF-08) and on regenerating the identity. A reconnection mid-transfer: it fails the transfer, with no resume — the user offers again.
10. **Partial PWA support on iOS (issue #104, 10.9)**: Safari allows adding gritos to the home screen, but there is no install prompt and the service-worker/standalone support has gaps — installation and the offline shell are best-effort there; Android/Chrome and desktop Chromium are the reference platform.

### 12.1 Design note: forward secrecy in DMs (issue #25)

**Status: the minimum viable is implemented (issue #93).** The v2 derivation of 9.2 is in production, with three deliberate deviations from what is sketched here:

1. **The ephemeral key travels in a dedicated directed action, `ephkeys` (7.1), not inside the `keys` payload.** A compound announce would have forced v1 peers to discard the whole set —the identity keys too—, breaking their TOFU view in mixed rooms.
2. **The mixed-version degradation is not only silent.** The silent discard of envelopes continues (7.3), but the new peer marks the v1 peer without an `ephkeys` announce as legacy and disables the composer with the "This peer runs an older version without per-session encrypted DMs" notice, instead of letting you write to a mailbox nobody will open.
3. **The identity→ephemeral binding uses the dual salt** (both fingerprint pairs in the HKDF salt, 9.2): signing the ephemeral key with the identity key proved unnecessary.

**Threat — _harvest now, decrypt later_.** The `dm` send is already **directed at the recipient** (7.1; issue #18, implemented), so the room's other members stopped capturing the encrypted envelopes. Before the migration, the residual recording surface sat at the conversation's ends: the DM key was derived from a **static-static** P-256 ECDH (9.2) between long-lived identity keys, so a single later compromise of one private key (device access, a `localStorage`/IndexedDB dump, a cryptanalytic advance) sufficed to decrypt **the entire recorded history** of that peer pair. 9.5 records it as an accepted v1 risk; this note fixed the migration, now materialized.

**Minimum viable: per-session secrecy.** Derive the DM key from an ECDH pair **ephemeral per app session**, announced to the peers of each room (implemented as the dedicated `ephkeys` action; deviation 1 of the Status): 9.2's ECDH stops using the identity private key and uses session-ephemeral material instead. The long-lived identity key and its fingerprint remain the TOFU anchor: they are displayed in the peer list and in the DM header for manual verification (RF-04, 9.1). Consequences to document:

- The `gritos:tofu` pin (8.2, issue #22) must keep pinning the **identity** fingerprint, never the ephemeral key's (which changes every session and would break the pin on restart).
- Each peer must bind identity → ephemeral key without opening the door to impersonation: the ephemeral key travels signed by the identity key, or 9.2's salt is derived from both fingerprint pairs (identity and ephemeral), so that a substituted ephemeral key does not derive the same key (implemented: the second option —the dual salt—; deviation 3 of the Status).
- The exposure window shrinks from "the identity's whole life" to "one session": what was recorded stops being decryptable when the tab closes; what was captured before the migration stays exposed.

**Complete solution (outside v1's scope).** _Prekeys_ announced per peer and an X3DH-style establishment with a _double ratchet_ per conversation (forward secrecy and post-compromise recovery, Signal-style). It requires a prekey announce channel and per-conversation ratchet state; the directed send it builds on is already implemented (7.1, issue #18). It is issue #93's phase B and remains future work.

**Migration discipline.** The v1 format is fixed by contract as legacy: derivation with `info = 'gritos/dm/v1'` over the sorted-fingerprint salt (9.2) and a `dm` envelope `{iv, payload}` (7.2). Any change to the derivation inputs (key pair, salt, info) or to the wire format must **increment a version marker** and be test-controlled, so that old and new peers never silently derive different keys from the same envelopes. The v2 migration materialized exactly that marker: `DM_KEY_INFO_V2 = 'gritos/dm/v2'` and Envelope `v: 2`, both pinned by guard tests (`DM_KEY_INFO` keeps `'gritos/dm/v1'` as the legacy format's constant, no longer sent nor accepted). In rooms with mixed versions, the envelopes that fail to open are silently discarded (7.3) —and the new peer additionally shows the explicit legacy-peer state (deviation 2 of the Status)— until the builds converge.

### 12.2 Design note: trackerless DMs — manual peer connection (issue #97)

**Status: implemented (issue #97).** What is sketched here is in production with no deviations from what was decided: the engine (blobs, state machines, `{"action", "payload"}` frames, dedup) lives in `lib/p2p/manualPeer.ts` —the only `RTCPeerConnection` surface—, the UI-facing manager in `lib/p2p/manualDmManager.ts` (the roomManager's mirror for the manual path: it feeds the store's `manualDms` slice, 8.1, and sets the TOFU pins under 8.2's reserved `manual:` prefix) and the wizard covers both roles with the strings in `settings/messages.ts`. The note's two invalidations are seams: RF-07 (regenerating the identity) destroys the pending flows and kills the live channels via the `onSessionIdentityRegenerated` subscriber the manual manager installs, and panic (RF-08) aborts them in the same pass (`abortAllManualDms`). What follows is the approved design note the implementation followed. A direct 1:1 channel (a WebRTC DataChannel) established by hand-exchanging two invite blobs —copy/paste today, an optional QR later—: the signaling needs no trackers or server at all, the only discovery path with literally zero infrastructure (11.2, 11.7). Everything else is reused intact: the DM v2 derivation (9.2), `dm` v:2 envelopes (7.2), receipts and typing (7.1), TOFU (8.2) and the `DmChannel` state (8.1). Manual peers share no swarm: what Trystero does in rooms, here the human pasting does it. Strict scope: a 1:1 DM.

**The invite envelope (blob).** Each role emits a single self-contained blob, JSON → standard base64 (decoded tolerating the spaces and line breaks the clipboard adds):

```jsonc
{
  "v": 1, // the blob format's version — unrelated to the envelopes' `v` (7.2)
  "role": "invite", // "invite" (offers) | "answer" (answers)
  "nick": "fox-bold", // advisory, never verified: identity is the fingerprint (9.1)
  "fp": "A31F 09BC 77D2 4E5A 51C0 FFEE 1234 5678", // identity fingerprint (9.1)
  "idKey": "<base64>", // the raw identity public key, 65 B (9.1)
  "ephKey": "<base64>", // the raw session-ephemeral public key, 65 B (9.2)
  "sdp": { "type": "offer", "sdp": "v=0…" }, // the RTCPeerConnection's localDescription
}
```

A raw SDP runs 2–4 KB; with the two keys and the JSON → base64 packaging, the blob lands at ≈3–6 KB — comfortable to paste over any channel. **No-trickle ICE**: the blob is only emitted when candidate gathering completes (`icegatheringstate === 'complete'`, with a 5 s guard that emits with what was gathered if a candidate lags) — after pasting there is no signaling channel to send late candidates to, so the blob must carry them all. The receiver validates before touching the network: a known `v`, a `role` consistent with the SDP's `type` (`invite`⇔`offer`, `answer`⇔`answer`), keys of exactly 65 B and a **fingerprint recomputed from the raw key** — a blob whose `fp` does not match SHA-256(`idKey`) is rejected as corrupt or tampered with; a missing or malformed `ephKey` invalidates the whole blob. 12.1's legacy-peer degradation does not exist here: #93's v2 capability is announced inside the blob, not in a later action.

**Key agreement: the v2 derivation of 9.2, unchanged.** Each blob carries BOTH public keys of its author (identity + session ephemeral), so when the exchange completes, each end knows the other's four fingerprints and raw ephemeral key, and derives exactly as 9.2 point 4 — ephemeral-ephemeral ECDH, `dmKey = HKDF-SHA256(secret, salt = SHA-256(the four canonical fingerprints sorted), info = "gritos/dm/v2")` — with the same dual salt binding identity→ephemeral: a substituted ephemeral in the blob makes the GCM fail visibly (12.1, deviation 3). Closed decision: the ephemerals travel **inside the blob**, not over the data channel before the first payload — there is no shared swarm to hang an `ephkeys` on (7.1), the protocol stays closed in two pastes with no prior plaintext phase over the channel, and the trust surface does not grow: the channel over which the blobs are pasted is already presumed worthy of the out-of-band fingerprint comparison the user performs, and the dual salt neutralizes a substituted ephemeral. 9.2's TOFU discipline stays intact: only the identity fingerprint is pinned and displayed; the ephemeral never.

**TOFU by fingerprint (no peerId).** The manual peer has no Trystero peerId and `gritos:tofu` is `{peerId: fingerprint}` (8.2): the pin rides the SAME key, in the flat map, under the reserved `manual:` + canonical fingerprint prefix — `manual:<canonical-fingerprint>` → the fingerprint in display form, the same value convention as the room pins. It introduces no `localStorage` key (the five-key invariant, 8.2), the same panic wipes it with no new code (RF-08), it keeps the `string→string` format (any read-modify-write preserves it) and it inherits #23's _first-write-wins_ and prefix rule as-is. Persisting it buys what rooms could never have: the identity (9.1) survives the reload —unlike the peerId—, so a later invite from the same identity is recognizable ("you have already chatted with this identity"): the first time TOFU recognizes a peer across sessions. A regenerated identity produces another entry; the previous pin is kept (a public value, the same policy as in rooms).

**Security notes.** The SDP can contain network addresses: browsers mask host candidates as mDNS names (`*.local`) today, but srflx candidates still publish the public IP:port — that is why the wizard shows, before each blob is copied, the exact warning "The invitation may contain information about your network" (the UI phase moved it into `settings/messages.ts`). The blob's authenticity is **not** guaranteed by the transport: whoever controls the channel over which the blobs are pasted can substitute the keys — the trust anchor is the out-of-band fingerprint comparison, exactly 9.5's TOFU limit, and the UI requires it before the first message. The blob never contains message data: only public keys, the fingerprint and the SDP.

**Architecture rule.** An exact mirror of the roomManager rule: components never touch WebRTC — `RTCPeerConnection` may only appear in `lib/p2p/manualPeer.ts`, just as Trystero may only be imported in `lib/p2p/roomManager.ts` — and the rest of the code consumes the engine through its API and the store (8.1).

**No-goals.** **No manual peer acts as a relay**: no bridging into room meshes and 7.3's silence rule stays full (a received message is never relayed); no multi-party manual swarms — the scope is strictly the 1:1 DM. The channel persists nothing (like today's DMs) and does not replace roadmap item 3: they are complementary solutions to the same limitation 11.7.

**State machines and reconnection.** Role A (creates the invite): `idle → invite-ready` (the blob is emitted when ICE gathering completes) `→ answer-pasted` (the answer validated and the fingerprint compared) `→ connected`. Role B (answers): `idle → invite-pasted → answer-ready → connected`. The waits placed on the human (for the other to paste) have no wall-clock timeout — only explicit cancellation, which closes the `RTCPeerConnection` and empties the pending state; the machine waits do: ICE gathering with the 5 s guard and establishment with 10.3's 15 s heuristic, which on expiry show a visible error and allow a retry (RNF-07). An answer whose fingerprint differs from the one the pending channel expects is rejected with an explicit error: it never silently opens a new channel. Connection drop (`iceconnectionstate` failed/closed or the DataChannel closed): the channel moves to RF-04's "The peer has disconnected" state (`available: false`, history in memory until reload); reconnecting demands a fresh blob exchange —the old connection is not reused and the blobs are single-use— and it resumes the SAME channel, keyed by the fingerprint, with history intact. Regenerating the identity (RF-07) or panic (RF-08) destroys the pending invites and answers: it is all ephemeral state, there is nothing persisted to clean; the live channel dies with its keys and the previous identity's `manual:` pin is kept.

**Wire reuse.** The DataChannel speaks the same `dm` semantics of 7.1: v:2 envelopes sealed per 9.2, ✓/✓✓ via batched `receipt` ≤50 with the same debounce, `typing` `{on, dm: true}` (all typing on the manual channel is DM typing), the 4000-character limit and the optional `ttl` (#96) intact. The minimal framing decided: **JSON text frames, one message per frame, `{"action": "dm" | "typing" | "receipt", "payload": …}`** — the substitute for Trystero's action routing —, with each payload validated by the already-existing rules (`parseEnvelope` for `dm`, `validateReceipt` for receipts). The manual path dedups with its own `BoundedSeenIds` (the same cap) and #19's freshness window, like the room paths (7.3). No chunking and no binary payloads: a sealed 4000-character `dm` runs about 5.4 KB, far under 7.3's 64 KB cap — there is no chunking decision to make; `presence`, `keys`, `ephkeys` and `ping`/`pong` do not exist on this path — the keys travel in the blob and latency is not measured in DMs.

**UI contract (contract level only; details in phase 3).** Entry: "+ invite" in the sidebar's DM section and the shortcut on the tracker-error banner; a wizard with both roles (create → copy blob → the other answers → paste answer → connect); on connecting, it lands in the standard DM view with `DmHeader` showing the fingerprint and the TOFU notice before the first message, and the manual channels are listed in `DmList` with the "(no room)" marker. The strings live in `settings/messages.ts`, with the wizard's focus-trap (`useFocusTrap`).

### 12.3 Note: mixed-build spike for the `react` action (issue #98)

**Status: resolved by source analysis; the feared fallback is unnecessary.** Before registering `react` (7.1), the source of `@trystero-p2p/core` 0.25.4 (`node_modules/@trystero-p2p/core/dist/action-wire.mjs`) was analyzed and an extra action on new builds proved harmless to the old peers of the same room. First, routing goes BY NAME, not by negotiated index: every wire chunk embeds the action's own name, zero-padded to 32 bytes at offset 0, and there is no handshake assigning names to ids per connection — a new name cannot displace the encoding an old peer parses for its existing actions (each message is self-describing). Second, on reception, a name missing from the local registry is reassembled all the same but parked in `pendingActionPayloads` without firing a handler or throwing: an old build ignores `react` traffic silently and its own actions keep routing intact (Trystero's internal actions use the `@_` prefix, with no possible collision against `react`). Accepted residual: that buffer of unclaimed payloads grows unbounded on the old peer (Trystero's own design) — the 30-payloads-per-peer-per-minute send cap and the payload's cosmetic size keep the contribution of honest builds insignificant. The operated conclusion: `react` was registered as its own action (7.1) and the issue's fallback — directing the reactions through the `receipt` channel — is rejected.

### 12.4 Design note: P2P file transfer over DataChannel (issue #103)

**Status: implemented (issue #103).** What is sketched here is in production: the engine —framing, credit window, caps, state machine— lives in `lib/p2p/fileTransfer.ts`, the binary chunk sealing in `lib/crypto/chunkCipher.ts` (`sealChunk`/`openChunk`, phase 2) and the UI (phase 4) in the composer's pre-send dialog, the `useFileTransfers` bridge and the strip of consent/progress cards under the feed; the roomManager registers the five actions and applies the mute gate (issue #95) before any parsing. The four points the note left to the engine's interpretation settled thus: the wire cannot tell a password-room chunk from a DM one, so the receiver tries the room key and then the DM key and the GCM AUTHENTICATION picks —neither ever authenticates the same chunk; the winner is fixed for the whole stream—; `file-end` leaves right after DISPATCHING the last chunk (it is the "last dispatched" signal, not an ack barrier: the final `nextSeq = chunks + 1` ack is what completes the sender); the window slides through acks that re-grant the FULL window when the receiver exhausts the granted one (not one credit per chunk); and a gapped chunk is DROPPED —the contiguous discipline (`seq === contiguousNext`): repeats, out-of-range and gaps fall, and a broken stream dies by the 30 s stall or by `file-end`'s fail-fast—. What follows is the approved design note the implementation followed. The transport already exists (Trystero's data channels, 6.3) and the crypto is reusable (9.2, 9.3), so a file inherits the confidentiality of the conversation it is sent in instead of trusting DTLS alone. Strict v1 scope: a **directed 1:1** transfer — the sender offers the file to each peer separately and only whoever ACCEPTS receives bytes; "a file for the room" is N independent transfers, one per consenting peer. Broadcasting to the whole mesh is rejected twice over: it would deliver bytes to peers without consent and multiply the traffic by the room size (mesh amplification) — the declining peers would pay for other people's bandwidth. Each transfer carries its own consent card, its own credit window and its own cancellation.

**New actions (7.1).** Five own actions, all directed at the peer (`{target}`, like `dm`/`receipt` — directing is the SENDER's discipline: Trystero cannot tell a directed send from a broadcast on reception, so the receiver additionally validates each payload against ITS active transfers from THAT peer and discards whole and silently (7.3) any traffic that does not correspond to a known transfer):

- `file-meta {id, name, size, mime, chunks, enc}` — JSON: the offer. Before acceptance not a single byte flows.
- `file-chunk` — binary (`Uint8Array`): the data, with the exact framing below.
- `file-ack {id, nextSeq, grant}` — tiny JSON: the receiver's credit (the credit window, below). It is a NEW action, not an overload of `file-end`: mixing flow control with closure would make the terminal state depend on an optional field.
- `file-end {id}` — JSON: the SENDER's close ("last chunk dispatched"); the receiver uses it to fail fast when a chunk is missing instead of waiting out the stall.
- `file-abort {id}` — JSON: cancellation by either party or offer rejection.

Registration: the five are registered together in `createConnection`'s action block (roomManager), after `hist` and before `ping`/`pong`, in the order `file-meta` → `file-chunk` → `file-ack` → `file-end` → `file-abort` (the reading order: offer, data, credit, close). The order is NOT load-bearing: by 12.3's analysis, actions route by name and an old build parks the payloads of unregistered names without firing a handler — silent degradation with mixed builds, no fallback.

**The `file-meta` validation contract (`parseFileMeta`).** Any violation discards the ENTIRE payload (7.3, the receipt/react discipline):

- `id` — a non-empty string; the transfer's key on both ends (the sender uses `crypto.randomUUID()`; the receiver demands no UUID format, only non-empty).
- `name` — sanitized with issue #28's remote-nickname discipline (the same control and invisible characters out, trimmed), with its own 120-character cap (`FILE_NAME_MAX_LENGTH`) — a legitimate file name is longer than a nickname. If sanitizing leaves nothing readable, the whole meta is invalid: the name IS the consent card and has no fallback line.
- `size` — an integer in 1..`MAX_FILE_BYTES` (20 MB). Non-integer, 0, negative or over the cap → invalid.
- `chunks` — an integer and EXACT: `chunks = ceil(size / FILE_CHUNK_PAYLOAD_BYTES)`. The count is not the sender's to govern: the receiver recalculates it from `size` and discards the meta if it differs — it closes the door on "declare small, send big" and on its inverse.
- `mime` — a string of ≤ 100 characters (`FILE_MIME_MAX_LENGTH`) with no control or invisible characters (the same class as #28's); empty is legitimate (a `File` with no known type arrives with mime `''`). It is never trusted: it is display-only — neither validation nor security depends on the declared mime (phase 4's image rendering uses it as a presentation hint, never as a permission).
- `enc` — a boolean REQUIRED, with no default: it governs each chunk's cryptographic path; absent or not a boolean → invalid.

Offer cap: `FILE_OFFER_RATE_CAP = 5` `file-meta` per peer per minute; the excess is silently discarded (the same mitigation class as the reactions in 9.5: the card costs attention, not memory).

**Binary framing of `file-chunk`.** The exact frame: `[8 B fileId ‖ uint32 BE seq ‖ payload ≤ 16 384 B]` — total ≤ 16 KiB + 12 header bytes (16 396 B), comfortably under `MAX_PAYLOAD_BYTES`'s 64 KB cap (7.3) even after Trystero's transport framing (the action name padded to 32 B plus per-chunk headers of ~16 KiB chunks: ~48 B more per chunk, 12.3).

- `fileId` — the 8-byte prefix = **the first 8 bytes of the SHA-256 of the meta's `id`** (UTF-8). The 36-character UUID v4 does not fit in 8 bytes and truncating the STRING to 8 would leave ~32 usable bits (hex); the truncated hash spreads 64 uniform bits. With ≤ 3 concurrent transfers per peer (both sides), the birthday bound over the ~6 identifiers in play gives p(collision) ≈ 8×10⁻¹⁹ — negligible by design, and the receiver moreover matches the prefix only against its active transfers from that peer.
- `seq` — a 1-based big-endian uint32: `1..chunks` (the last chunk carries `size mod FILE_CHUNK_PAYLOAD_BYTES`, which is never 0: with `size` an exact multiple, the last chunk goes full). Out of range or repeated → the chunk is dropped.
- `payload` — a slice of the file. The PLAINTEXT slice is `FILE_CHUNK_PAYLOAD_BYTES = 16 356` (16 KiB − 28 B of IV+GCM tag) in BOTH modes, so `chunks` does not depend on the mode and the sealed payload fits exactly in 16 KiB: in the clear it travels as-is (≤ 16 356 B) and sealed it grows by 28 fixed B (12 of IV + 16 of tag) → ≤ 16 384 B. An unsanitized plaintext slice exceeding the slice invalidates the stream; on completing the `chunks` chunks, the plaintext sum must be EXACTLY `size` — any deviation → `failed`.

**Credit window (receiver → sender flow control).** `FILE_CREDIT_WINDOW = 8` unacknowledged chunks in flight at most. The receiver grants the first window upon ACCEPTING — there is no separate "accept" action: the first `file-ack {id, nextSeq: 1, grant: 8}` IS the acceptance and starts the flow. On every ack, `nextSeq` is the next expected sequence (everything before arrived contiguously) and `grant` are fresh credits (0..FILE_CREDIT_WINDOW; the receiver grants the full window on every ack). Sender invariant: sent-unacked ≤ FILE_CREDIT_WINDOW; a chunk is acknowledged when a `file-ack` announces `nextSeq > seq`. Close: on gathering the `chunks` chunks, the receiver emits the final ack `{id, nextSeq: chunks + 1, grant: 0}` and the sender moves to `done` with it. Anti-deadlock: `FILE_STALL_TIMEOUT_MS = 30_000` with NO progress whatsoever (a new chunk at the receiver, an ack at the sender) in `transferring` → `failed` on both ends and immediate release of what was accumulated. The offer itself has no wire timeout: it dies by explicit decline (`file-abort`), by the peer dropping or with the session (all in memory). A chunk exceeding the granted credit is DROPPED — the window is the receiver's memory plan; an honest sender never does it and a systematic violator runs out the 30 s stall. Chunks of unknown transfers or not in `transferring` → silent drop.

**Encryption: seal before framing (seal-then-frame).** `meta.enc = true` (password rooms: 9.3's room key; DMs: 9.2's DM v2 key) → the payload of EVERY chunk travels AES-GCM-sealed BEFORE framing: the 16 KiB cap applies POST-sealing (the arithmetic above) and the frame stays fixed whichever the mode. The sealing's binary format: exactly 9.3 step 3's / 9.2 step 4's without the base64 layer — `bytes(IV ‖ ct)` with a random 12 B IV per chunk and a 16 B GCM tag (phase 2 added the binary `sealChunk`/`openChunk` variants; the current helpers are string→base64 and are not reused as-is, to avoid inflating base64's ~34 % into binary). **No additional salt**: the keys are already bound to the conversation (9.3: derived from password+name; 9.2: the dual salt of the four fingerprints) — reusing them as-is inherits their guarantees, and the random per-chunk IV needs no counter: with ≤ 1,283 chunks per transfer (20 MB / 16,356) and ≤ 3 transfers per peer, the collision probability of a 96-bit IV is of the same negligible order as the chat messages'. The offer's metadata (`name`, `size`, `mime`) travels in the clear in `file-meta` — the same exposure as `presence`'s nicknames; only whoever holds the key reads the CONTENT. Sealing it would demand a v2 of the file protocol: future work. Public rooms: `enc = false` → DTLS only, with an explicit pre-send warning (phase 4) and a consent card showing the state: "encrypted with the room key" / "encrypted E2E with the DM key" / "no E2E encryption — DTLS only".

**State machine and reconnection.** Canonical per transfer: `offer → accepted → transferring → done | aborted | failed`, with `rejected` as an immediate branch of the offer. Each role fires the transitions:

- Sender: `offer` (the meta sent; awaits the first `file-ack` or a `file-abort`) → `accepted` (the first ack arrives: consent confirmed) → `transferring` (credit active, chunks leave; in practice the same instant) → `done` (the final `nextSeq = chunks + 1` ack) | `aborted` (the receiver's `file-abort` — the offer's rejection reads here as `rejected` — or a local cancellation, both with a `file-abort` to the other side) | `failed` (the 30 s stall, the peer dropping).
- Receiver: `offer` (the card visible; NO byte flows) → `rejected` (declining: `file-abort` and release) | `accepted` (a tap on accept) → `transferring` (the first `file-ack` with the window leaves) → `done` (chunks complete, exact sum, a Blob and the object URL) | `aborted` (a local cancellation or the sender's `file-abort`) | `failed` (a chunk that would exceed `size`, an invalid frame, a GCM failure, the 30 s stall, the peer dropping).

Reconnection mid-transfer: **the transfer fails, with no resume** — offsets, windows and accumulators live in memory per connection, and resuming would demand persisted state, contrary to the product's total ephemerality. Documented as a limitation (the docs phase carries it to §11 and the README): the user offers again.

**Caps.** `MAX_FILE_BYTES = 20 × 1024 × 1024` (20 MB) — the RECEIVER's hard cap: a meta over the cap is invalid and a chunk whose plaintext would push the accumulated total past `size` aborts the transfer ON THE FIRST exceeding byte, without waiting for the rest of the chunk. `MAX_TRANSFERS_PER_PEER = 3` concurrent transfers per peer, on BOTH sides — the fourth simultaneous offer from the same peer is answered with a `file-abort` (an explicit rejection, so the sender's UI says "the peer is busy" instead of a silence). Chunk payload: 16 KiB post-sealing (16,356 B of plaintext). Name sanitized and bounded to ≤ 120 characters. Worst-case budget: 3 × 20 MB = 60 MB of RAM per peer and direction — the number QA will exercise.

**The issue's throughput spike closes here by framing arithmetic.** Chunks travel over THE SAME data channels as the chat (Trystero's torrent strategy) and each `file-chunk` is its own binary action of ≤ 16 396 B — independent of the 64 KB cap of the chat actions, with no framing interaction with the `hist` batches. A conservative bound: reliable, ordered WebRTC channels; even at 200 KB/s a 20 MB file completes in ~100 s (at 1 MB/s, ~20 s), and the K=8 window (~128 KiB of plaintext in flight) limits memory pressure, not the speed ceiling. Phase 3 opens with the LIVE measurement the issue demands; if it measured slow, the framing margin allows raising the payload to ~48 KiB by changing ONLY constants (the frame still fits comfortably under 64 KB) — a noted contingency, with no re-deciding of the design.

**Memory and revocation: RAM only.** The receiver accumulates chunks in an in-memory array → `new Blob(parts)` on completion → `URL.createObjectURL`; the sender never loads the whole file (`File.slice()` per chunk, phase 3). The URL is revoked (`revokeObjectURL`) on dismissing the `done` card, on aborting or failing (with the partial accumulation), with panic (RF-08) and on regenerating the identity (the same seam as the manual DMs, 12.2); a reload loses it all. Nothing touches `localStorage` or IndexedDB: the five-`gritos:*`-keys invariant (8.2) stays intact — with no new key, panic needs no extra wiping code.

**Interactions.**

- Mute (issue #95): the FIVE file actions of a muted peer are discarded before any parsing or effect (the same gate as `chat`/`dm`/`typing`: they are content). Muting a peer with an active transfer aborts it on the spot locally (with a `file-abort` to the other side): a muted peer's content stops accumulating immediately.
- TTL (issue #96): does NOT apply to the files — they are not feed rows.
- Store representation (8.1): **the `fileOffers` map, not a feed row.** `fileOffers: Record<string, FileTransferRecord>`, keyed `${peerId}:${meta.id}` (the counterpart's peerId keeps two peers choosing the same id from colliding), memory-only, never persisted. The decision: the 500 FIFO and the TTL sweep govern MESSAGES and must never revoke a URL nor evict a file mid-view — the offer/progress/result card lives and dies with its map record (offer → done/rejected/aborted/failed → the user's explicit dismissal). Phase 4 renders the card from the map (its feed position and visual detail are its own) and, should it add context rows to the feed, they will be display-only: the blob's, the URL's and their revocation's ownership is ALWAYS the map's. Zero arrival effects: no file action marks unread, notifies, receipts or mentions (7.3's silence) — the card IS the disclosure.

**No-goals.** **No transfer is ever broadcast to the room** — directed 1:1 to each accepting peer, never broadcast (consent + amplification). No resume (a reconnection = `failed`). No directories: a flat file per transfer. No thumbnails: images render from the received blob, only after completion. No persistence of anything (not even metadata). No compression and no sealed meta (future work; it would demand a v2 of the file protocol).

### 12.5 Design note: global signaling channel — fingerprint knocks (issue #105)

**Status: implemented (issue #105).** What is sketched here is in production: the constants and payload validators live in `lib/p2p/signalChannelConstants.ts` —their single home, next to no other module—, the swarm manager in `lib/p2p/signalChannel.ts` (join/leave bound to `Settings.globalDm` by subscribing to the settings store — panic RF-08 traverses it when resetting —, the LRU presence, the knock budget, the mute gates and the `dm`/`typing`/`receipt` transport), the `DmTransport` interface in `lib/p2p/dmTransport.ts` — BOTH backends, room and signal, behind the same minimal surface — and the contact flow (phase 3) at the "+ contact" entry of `DmList`: "My contact" (a copyable fingerprint plus the `#contacto=<fp>` QR, #100's machinery) and "Contact by fingerprint" (paste a fingerprint → knock → a cancellable wait), with the consent cards under the chat area. The four points the note left to the phases' interpretation settled thus: the signal-backed channels live in the SAME `dms` slice of the store (8.1) keyed by the canonical fingerprint with the additive `global: true` marker — the "(global)" sibling of the manual "(no room)" —, and they do not collide with the room ones because the keys are disjoint namespaces (Trystero peerIds of ~46 characters versus 32 hex); the TOFU pins (8.2) are only written when a channel is OPENED — accepting, sending or receiving a `dm` —: presence alone never touches `gritos:tofu`, so sweeping the swarm cannot leave behind a persisted stranger directory (the no-directory restriction holds on disk too); the consent cards are NON-blocking — a `role="status"` strip under the chat area, one per distinct knocker (the latest wins), never a modal a spammer could open —; and the `onKnockResolved` seam resolves ONCE per acknowledged knock, AFTER opening the channel — a knock without an ack (the peer left, the ack was lost) never resolves: the wait dialog stays cancellable, with no wire timeout (a documented limitation of the seam) —. What follows is the approved design note the implementation followed. The product constraint that rules over everything else: the channel is dumb — it exists only so that two fingerprints can find each other when BOTH sides opted in, it carries knocks and keys, never conversation content, and it is **not** a global presence directory.

**The signaling swarm (phase 2).** A room derived like any other (9.4) from ONE constant, `SIGNAL_ROOM_NAME = '_gritos/senal/v1'`, defined in a single place (`lib/p2p/signalChannelConstants.ts`): `deriveSignalRoomId()` = `deriveRoomId(SIGNAL_ROOM_NAME)`, with the same hash asynchrony. Only the builds sharing the same `VITE_TRYSTERO_APP_ID` (issue #90; 9.4) see it: the appId is the discovery namespace, so forks and self-hostings have disjoint global channels with no new code. The name is unreachable from the rooms UI — RF-02's character set (`[a-z0-9_-]`) excludes the `/`—: nobody enters the channel through the join popover; only the signal manager joins it. Mixed-build degradation does not apply by construction: a build without the setting (or older than #105) never joins — there is no old peer INSIDE the swarm, and an unknown action between channel peers resolves per the 12.3 spike's conclusion (the payload stays parked with no handler, no error).

**Swarm actions (the phase-2 contract).** Three own ones, plus the two key actions reusing the room mold as-is:

- `whoami {nick, fp}` — broadcast on connect and on nickname change: the channel's presence (the `presence` mold, 7.1).
- `knock {type:'knock', from:{fp, nick}, note?}` — **directed** at the destination peer: the door. No content field: the optional note of ≤ 140 characters (`NOTE_MAX_LENGTH`) is ALL a knock can say.
- `knock-ack {accept, fp}` — **directed** back at the knocker: `accept` is the consent and `fp` is the fingerprint of the knock being acknowledged (the knocker's, an echo of the received `from.fp`) — the knocker may be awaiting several acks and matches theirs by fingerprint.
- `keys` / `ephkeys` — announce as in a room (7.1): the signal-backed DM's key resolution is EXACTLY 9.2's v2 derivation, with the ephemeral announced ON the signal swarm; the TOFU anchor remains the identity fingerprint (8.2) and the self-declared `fp` of `whoami`/`knock` is advisory, like `presence`'s in a room.

**Validation contract (the `parseReact`/`parseHistReq` discipline; 12.4).** Any violation discards the ENTIRE payload silently (7.3) — never just the field:

- `parseKnock` — a plain object with an EXACT `type` of `'knock'`; `from` an object with `fp` in canonical form (issue #95's rule: `canonicalFingerprint` → exactly 32 hex; stored normalized) and a `nick` that survives the remote-nickname sanitization whole (issue #28): if nothing readable remains, the whole knock is invalid — the nickname IS the consent card, with no fallback line (the same reason as `file-meta`'s `name`); `note`, when present, is a string of ≤ 140 characters IN RAW FORM (the excess is hostile input: an honest sender never fills it) sanitized with the same #28 class — a note left empty by sanitizing is treated as absent (the field is optional and carries no protocol semantics).
- `parseWhoami` — `{nick, fp}` with the same canonical-`fp` and readable-`nick` rules; the presence list has no fallback row per peerId (it is not a room's listing: it is the minimum state to resolve knocks and keys).
- `parseKnockAck` — `{accept, fp}`: `accept` a boolean REQUIRED with no default (it governs opening the channel) and a canonical `fp` — that of the acknowledged knock; an ack that does not match a pending knock of one's own is discarded at the manager layer (phase 2).

**Caps (phase 2 implements them).** `MAX_SIGNAL_PRESENCE = 100` presence entries with LRU eviction — the 101st evaporates the oldest seen; it is engine state, never a browsable UI listing: the only discovery path is the fingerprint knock. `KNOCK_RATE_CAP = 5` RECEIVED knocks per peer per minute; the excess is silently dropped (the same mitigation class as `FILE_OFFER_RATE_CAP` in 12.4). The presence re-announces are not periodic: connect and nickname change only, like `presence` in a room (7.1) — a noisy peer finds no action to be noisy with.

**Lifecycle bound to the setting.** Joining and leaving are strictly bound to `Settings.globalDm: boolean` — **default false** —, which lives inside `gritos:settings` (8.2: no seventh key; panic RF-08 wipes it with the rest of the setting). The toggle goes in Settings → Privacy (phase 2). Turning it off leaves the swarm ON THE SPOT (`leave`) and destroys ALL the channel's in-memory state — presence, knock budget, pending acks — and any DM channel backed by it (the same seam as `abortAllManualDms` in 12.2; the affected channels move to "The peer has disconnected", RF-04). Turning it on rejoins and re-announces. Neither state touches any persistence: the global channel adds NOTHING to `localStorage` (the five-key invariant, 8.2).

**DmTransport (the phase-2 refactor).** A minimal interface from which BOTH possible backends of a `DmChannel` (8.1) hang — the room swarm (today) and the signal one (new) —, so the UI and the store ignore the difference: `sendDm(envelope)` (9.2's sealed `dm` v:2 envelope, directed), `sendTyping(on)` and `sendReceipts(ids)` (7.1 as-is), `available` (RF-04's "peer disconnected" state) and key resolution — the v2 derivation UNCHANGED (9.2): identity and ephemeral announced on the swarm backing the channel, dual salt and TOFU intact. The signal-backed channels are addressed by FINGERPRINT — the swarm's peerId is ephemeral per session and the fingerprint is THE product's address (9.1), precedented by 12.2's `manual:<fingerprint>` keying — and they feed the SAME `DmChannel` slice of the store: in `DmList` they carry the "(global)" marker (the sibling of 12.2's "(no room)") through an additive boolean in the style of `manual?`.

**Contact flow (the phase-3 contract).** Two entries:

- **"My contact"** shares YOUR fingerprint: clipboard copy from day one, and a QR through #100's machinery (10.8) with a new hash parameter, `#contacto=<fp>` — the SAME discipline as `#sala=`: an optional leading `#`, percent-decoding tolerated, and the value is the fingerprint in canonical form (32 hex; the display form's spaces are tolerated and canonicalized with issue #95's rule) —, never a nickname or a password; a value that does not canonicalize to 32 hex does not route. Like every link of the app, it only works within this same installation (same origin and same appId, 10.8).
- **"Contact by fingerprint"**: paste a fingerprint → look it up in the channel's presence → `knock` → a consent card at the destination: "@nick wants to open a DM with you — [Accept] [Decline] [Mute]". Accepting answers `knock-ack {accept: true}` and BOTH sides open the signal-backed channel. Declining answers `accept: false` and **does not remember the rejected sender** — no contact store: per-session state, consistent with ephemerality (D2); the mute list (issue #95) DOES persist and mutes the knocker (12.4's gate: a muted peer's knock is discarded before parsing). "Mute" does both at once: `accept: false` plus the persistent mute.

**§9.5 (the threat model's honesty).** Recorded IN 9.5: joining the global channel exposes IP, fingerprint and nickname to every opt-in peer; the default-off is the documented mitigation, and a knock reveals the knocker's interest — inherent.

**No-goals.** The channel never carries content — not even a "hello" smuggled in the `note`: the conversation only exists after consent, inside the E2EE DM. No browsable directory of global peers in the UI. No accounts, emails or usernames: the only address is the fingerprint (9.1). No sharding in v1: a single swarm; should popularity demand it, N signal rooms chosen by fingerprint hash is the future work sketched in the issue.

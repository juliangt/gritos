This is an excellent architecture proposal: **Trystero** solves precisely the WebRTC signaling by leaning on public BitTorrent trackers (through WebTorrent), achieving the initial _handshake_ without requiring any backend infrastructure of our own. Once the data channel is established (RTCDataChannel), traffic flows strictly peer-to-peer and encrypted at the transport level (DTLS-SRTP by WebRTC standard).

Presented below is the functional definition, the recommended technical architecture and the key questions to close the specifications.

---

## 1. Main Use Cases

1. **Entry and Fast Onboarding:**

- The user opens the URL and, if they have no profile, is asked for a _nickname_ (or a random, friendly one is autogenerated).
- They connect immediately to the default configured room (`#lobby`).

2. **Navigation between Rooms:**

- The user can pick predefined suggested rooms (e.g. `#general`, `#dev`, `#random`) or type the name of any free room ("creating" is joining a common hash at the tracker).
- When switching rooms, they either disconnect from the previous room or keep the connection in the background, depending on configuration.

3. **Real-time P2P Messaging:**

- Sending text, typing states (_typing indicators_), and delivery receipts in the current room.

4. **Encrypted Direct Messaging (1 to 1):**

- Private messages between two peers inside the same room or by node ID, with additional end-to-end encryption (E2EE) on top of the WebRTC layer.

5. **Network and Privacy Settings:**

- Configuration of connection behavior, alternative trackers, local persistence and full session wipe.

---

## 2. User Experience (UX/UI)

To keep the aesthetic **minimalist, fast and clean**:

- **Layout:**
- **Collapsible sidebar:** List of recent/favorite rooms, a button to join a new room and a list of active peers with visual latency and status indicators (connecting, connected, disconnected).
- **Main Area:** Header with the room name (`#room-name`), number of connected peers, a message feed with smart auto-scroll and a simple input field with basic Markdown support.
- **Settings Modal/Panel:** Configuration persisted in `localStorage` or `IndexedDB`.

- **Connection Feedback:**
- Clear states: _"Searching for peers on the torrent network..."_, _"Connecting (2 peers found)"_, _"P2P channel established"_. On networks based on BitTorrent trackers, _discovery_ usually takes 2 to 6 seconds; the UI should reflect this process subtly.

---

## 3. Recommended Technology Stack (Client-Side Only)

| Layer                 | Technology                                 | Justification                                                                                                                                      |
| --------------------- | ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **UI Framework**      | **React + Vite** (or **Svelte / SolidJS**) | Compiles to pure statics (`dist/` with HTML/JS/CSS) without a backend. React with Vite offers a mature ecosystem and robust typing tooling.        |
| **Styling**           | **Tailwind CSS**                           | Clean interface, utility-first design with no runtime overhead, native dark/light themes and outstanding performance.                              |
| **P2P Signaling**     | **Trystero** (`trystero/torrent`)          | Implements decentralized signaling over public WebTorrent trackers and abstracts the opening of WebRTC channels.                                   |
| **Global State**      | **Zustand**                                | Extremely lightweight, no boilerplate, ideal for decoupling network events from visual components.                                                 |
| **E2EE Cryptography** | **Web Crypto API** (browser-native)        | Avoids heavy dependencies. Makes it possible to generate asymmetric key pairs (ECDH P-256 or X25519) to agree on symmetric keys (AES-GCM 256-bit). |
| **Storage**           | **idb** (IndexedDB)                        | For local message history and local private keys without the risk of exposing data to external servers.                                            |

## 4. Technical Answers and Feasibility

- **Can the torrent tracker always be listening?**
- **Yes, as long as the browser tab is active.** Trystero keeps the WebSocket connections to the public trackers open (e.g. `wss://tracker.openwebtorrent.com`). Every new client that joins with the same `appId` and `roomId` requests the peer list and the tracker facilitates the exchange of SDP offers/answers. Once the WebRTC connection is consolidated, chat traffic travels directly between browsers.

- **Additional E2EE encryption:**
- Although WebRTC encrypts the transport channel mandatorily (DTLS), implementing an additional layer with the **Web Crypto API** guarantees that nobody on the network (not even an intermediary node if relay topologies were ever built) can decrypt the content.
- _Flow:_ When two clients connect, they publish their public key (ECDH). Via Diffie-Hellman they compute a shared secret and derive an AES-GCM key to encrypt the message payload before sending it over Trystero's DataChannel.

---

## 5. System Configurations to Include

1. **Network and Signaling:**

- Auto-join `#lobby` on start (enable / disable).
- Custom WebTorrent tracker list (as a fallback if the public ones fall or get saturated).
- Custom STUN/TURN servers (crucial for clients behind symmetric NATs or corporate firewalls where pure direct P2P usually fails).

2. **Privacy and Data:**

- History retention level: _Memory only (volatile)_, _Persist locally (IndexedDB)_, or _Zero history_.
- Instant purge button ("Panic button" to wipe keys, messages and the local cache).

3. **Experience:**

- Desktop notifications (Web Notifications API) for mentions or direct messages.
- Theme modes (Light / Dark / System).
- Generation/regeneration of the cryptographic identity.

---

## 6. Questions to Define the Specifications (Specs)

1. **Room Topology:**

- Will a user be able to be connected to **multiple rooms simultaneously** (internal tabs in the background), or will switching rooms imply closing the previous room's connection to save WebRTC resources?

2. **Estimated capacity per room:**

- Trystero uses a full-mesh topology (_full mesh_), where each client connects to everyone else in the room. Optimal performance is usually 6 to 15 people per room. Does the use case target small/private groups, or are massive rooms foreseen (which would require another relay architecture)?

3. **History Persistence:**

- Since there is no server, a user who joins a room late sees no previous messages unless another connected peer relays them (_gossip / state sync_). Do you want to implement history synchronization between connected peers, or are messages ephemeral and only visible from the moment of connection?

4. **File Sharing:**

- Will the chat be strictly plain text/Markdown, or do we contemplate direct P2P file/image transfer via `sendAction` / DataChannels?

5. **Room Encryption vs. Direct Messages:**

- In the public shared rooms (like `#lobby`), should encryption be with a shared room password, or is E2EE only required for private 1-to-1 chats?
